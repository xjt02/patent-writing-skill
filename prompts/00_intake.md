# 00 — Intake（接收案件元数据）

> **阶段**：阶段 2 / 入口
> **触发**：用户提供"摘要"后第一个 prompt
> **输出**：标准化 intake JSON，传给 01～06

## 输入

用户口头/文件提供的：

| 字段 | 必填 | 备注 |
|---|---|---|
| 摘要正文 | ✅ | 任意长度的中文摘要 |
| 技术领域 | ⚠️ 可选 | 若缺，01_abstract_page 自动补全 |
| 案件标题 | ⚠️ 可选 | 若缺，03_claims 与 04_description 用"本发明" |
| 申请人 | ⚠️ 可选 | 仅用于文档元数据，**不写入正文** |

## 标准化输出

```json
{
  "case_id": "<YYYYMMDDHHmmss>",
  "title": "基于 XXX 的 YYY 方法",
  "abstract_raw": "用户原始摘要...",
  "technical_field": "工业现场智能监测",
  "applicant": "[申请人]",
  "created_at": "<ISO 8601>"
}
```

## 硬约束

1. `case_id` 用时间戳生成（命名规范：`专利_{YYYYMMDDHHmmss}.docx`，防覆盖）
2. `abstract_raw` 保留**用户原始文本**，不要改写
3. 缺失字段用占位 `"[待填写]"` 标记，**不得**填入虚构内容

## 摘要 4 要素检查（T3 压力场景）

对用户输入的摘要做 4 要素检查。**任意 1 项缺失即触发追问**：

| # | 要素 | 判定关键词（至少 1 个） |
|---|---|---|
| 1 | 技术领域 | 属于、涉及、应用、应用于、本发明公开 |
| 2 | 解决问题 | 解决、针对、改善、提高、降低、克服 |
| 3 | 技术方案 | 包括、采用、通过、基于、步骤、特征在于 |
| 4 | 有益效果 / 用途 | 可用于、适用于、因此、有助于、效果好 |

**追问协议**：缺哪项问哪项，**每次只问 1 个**：

```
Use AskUserQuestion:
  question: "你的摘要中未明确【解决问题】，请补一句：要解决什么技术问题？"
  header: "技术问题"
  options:
    - 现有方法准确率低（推荐）
    - 现有方法效率低
    - 现有方法成本高
    - 其他（用户输入）
```

**反例**（不要做）：
- ❌ 编造缺失要素（"我猜你想表达..."）
- ❌ 把 4 要素压缩到 1 个超长问题
- ❌ 跳过追问直接出文档
- ❌ 同一消息里问 2 个以上要素

## 收尾

- 把 intake JSON 写到 `assets/cases/{case_id}/intake.json`
- 进入 `prompts/01_abstract_page.md`
